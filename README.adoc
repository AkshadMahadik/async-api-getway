# Asynchronous API Gateway - Vert.x 5

A high-performance, non-blocking API gateway built with Vert.x 5 that aggregates data from multiple external APIs.

## Architecture
                                ┌──────────────────┐
                                │                  │
                        ┌──────▶│  Posts API       │
                        │       │  (External)      │
┌──────────────┐        │       └──────────────────┘
│              │        │
│   Client     │───────▶│  Circuit Breaker Layer
│              │        │
└──────────────┘        │       ┌──────────────────┐
                        │       │                  │
                        └──────▶│  Users API       │
                                │  (External)      │
                                └──────────────────┘
                                         │
                                         ▼
                                ┌──────────────────┐
                                │                  │
                                │  Aggregated      │
                                │  Response        │
                                └──────────────────┘

## Features

- **Parallel API Calls**: Uses Vert.x CompositeFuture for concurrent requests
- **Circuit Breaker Pattern**: Protects against cascading failures
- **Non-blocking I/O**: Fully asynchronous with Vert.x event loop
- **Error Resilience**: Graceful degradation and proper error responses
- **Monitoring Endpoints**: Health checks and circuit breaker status
- **Production Ready**: Docker support, logging, connection pooling

## API Endpoints

### GET /aggregate
Aggregates data from two external APIs in parallel.

**Response (200 OK):**
```json
{
  "post_title": "sunt aut facere repellat provident occaecati excepturi optio reprehenderit",
  "author_name": "Leanne Graham",
  "response_time_ms": 1234
}
```

**Error Response (502 Bad Gateway):**
```json
{
  "error": "Failed to retrieve upstream data",
  "details": "timeout",
  "response_time_ms": 5001
}
```

### GET /health
Health check endpoint for monitoring.

**Response:**
```json
{
  "status": "UP",
  "timestamp": 1698765432000
}
```

### GET /status
Circuit breaker status for debugging.

**Response:**
```json
{
  "posts_circuit": {
    "state": "CLOSED",
    "info": "SimpleCircuitBreaker[name=posts, state=CLOSED, failures=0]"
  },
  "users_circuit": {
    "state": "CLOSED",
    "info": "SimpleCircuitBreaker[name=users, state=CLOSED, failures=0]"
  }
}
```

## Configuration

Edit `AggregatorVerticle.java` to customize:
```java
// Server configuration
private static final int SERVER_PORT = 8080;
private static final long TIMEOUT_MS = 5000;
private static final int MAX_POOL_SIZE = 10;

// Circuit breaker configuration
```

### JVM Options
```bash
java -Xmx1g -Xms512m \
     -XX:+UseG1GC \
     -XX:MaxGCPauseMillis=200 \
     -jar target/async-api-gateway-1.0-SNAPSHOT.jar
```

### Vert.x Options
Modify `MainVerticle.java`:
```java
VertxOptions options = new VertxOptions()
  .setEventLoopPoolSize(8)
  .setWorkerPoolSize(20)
  .setBlockedThreadCheckInterval(5000);

Vertx vertx = Vertx.vertx(options);
```

## Circuit Breaker Behavior

The circuit breaker has three states:

1. **CLOSED** (Normal)
   - All requests pass through
   - Failures are counted
   
2. **OPEN** (Failure threshold reached)
   - Requests fail immediately
   - After reset duration → HALF_OPEN
   
3. **HALF_OPEN** (Testing recovery)
   - One test request allowed
   - Success → CLOSED
   - Failure → OPEN

Example flow:
CLOSED ──(3 failures)──▶ OPEN ──(10s wait)──▶ HALF_OPEN
▲                                              │
└──────────────(success)────────────────────┘

## Monitoring & Observability

### Logs
Logs are output via SLF4J. Configure `simplelogger.properties` in `src/main/resources/`:
```properties
org.slf4j.simpleLogger.defaultLogLevel=info
org.slf4j.simpleLogger.log.com.example.vertx=debug
org.slf4j.simpleLogger.showDateTime=true
org.slf4j.simpleLogger.dateTimeFormat=yyyy-MM-dd HH:mm:ss
```

## Troubleshooting

### Circuit Keeps Opening
```bash
# Check circuit status
curl http://localhost:8080/status

# Common causes:
# - External APIs are slow/down
# - Network issues
# - Timeout too aggressive

# Solutions:
# 1. Increase timeout in AggregatorVerticle
# 2. Increase failure threshold
# 3. Increase reset duration
```

### High Latency
```bash
# Check response times
curl -w "\nTime: %{time_total}s\n" http://localhost:8080/aggregate

# Solutions:
# 1. Increase connection pool size
# 2. Enable HTTP/2
# 3. Add caching layer
```

### Memory Issues
```bash
# Monitor heap usage
jstat -gc <pid> 1000

# Solutions:
# 1. Increase heap: -Xmx2g
# 2. Tune GC: -XX:+UseG1GC
# 3. Close WebClient properly
```
